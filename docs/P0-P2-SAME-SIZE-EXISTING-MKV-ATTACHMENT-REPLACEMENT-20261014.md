This is a bounded, user-visible existing-container edit, not a general Matroska writer or a replacement for the FFmpeg muxer.

## Product capability

The workbench now offers a separate opt-in path for a source that *already contains attachments*. A user chooses an **actual source Attachment FileUID**, selects one replacement File of **exactly the old FileData byte length**, sees which UIDs are blocked by existing TagAttachmentUID references, explicitly confirms the operation, generates a **new candidate MKV** and only after local byte- and inventory-verification may download it. Original source is never overwritten. Invalidations on changing the source, target, replacement file or review flag block the old plan/download.

No source chapters, tracks, Tags, SeekHead/Cues, Info, Segment layout or other original attachments are regenerated by this code. The new Blob consists of original prefix bytes + replacement FileData + original suffix bytes. The old FileUID, filename, MIME and FileData element header are retained; therefore the total Segment length and all existing byte offsets stay unchanged. The classic FFmpeg/Wasm remux is never invoked as a fallback.

## Strict gates

- Source must be 1–60 MiB; single new FileData must be 1 byte–4 MiB; *replacement.size === original FileData size*. Equal size is a byte-length guarantee, **not** evidence of equivalent semantic content.
- Source must be a Matroska with one existing Attachments master, media Tracks and Cluster, fully scanned and raw-byte-committed; no unknown top-level element, unknown Segment length or top-level CRC. A second independent attachment inventory must be inspected and checked for duplicate FileUIDs.
- Existing AttachmentUID-targeted Tag references are inspected from original EBML. **Any target matching the chosen FileUID blocks** the edit. Unknown/incomplete target graphs also block. Targeted Tags pointing to other attachments may remain, unchanged.
- The Attachments master and all AttachedFile children are parsed with bounded EBML header traversal. CRC-32 inside the master or any AttachedFile blocks; unknown children of the Attachments master, ambiguous FileData boundaries or unaddressable sizes block.
- Exact in-session source/replacement Blobs are privately held by WeakMap keyed by a frozen genuine plan. Hash original source FileData, replacement bytes and whole original source on prepare; verify their SHA-256 and exact lengths again at execution and after local output inspection. A serialized or cloned plan cannot execute.
- New output must retain the original file byte length, EBML/Segment header commitments, **every non-Attachments top-level EBML element commitment, ID, order and offset**, all attachment UIDs/names/MIME/description/data ranges, and all other FileData SHA-256. Only the chosen FileData digest is allowed to change.
- The shared raw preservation comparator's state remains `ATTACHMENT_DELTA_NEEDS_REFERENCES_OFFSETS_AND_WRITER_PROOF`, `approvedToWrite=false`. A bounded local candidate writer can produce a verified *new copy* without upgrading that separate universal semantic/writer contract.

## Independent evidence contract

`tests/existing-mkv-same-size-attachment-replace.test.mjs` creates structured EBML fixtures with nested chapter atom, targeted AttachmentUID Tag, two original attachments and media-like Track/Cluster. Positive case replaces the **untargeted** attachment only, checks whole-source SHA, byte-commitments, metadata and original targeted FileData. Negative tests cover wrong size, no-op, missing explicit consent, targeted UID, duplicate UID, enclosing CRC, unknown top-level EBML and forged plan.

`scenarioExistingMkvSameSizeAttachmentReplace()` in real Chromium E2E uses the independently `mkvmerge`/`mkvpropedit`-authored `p0-independent-attachmenttag.mkv`, adds independently authored nested Chapters, then replaces the **decoy** attachment with equal-byte-length bytes. The browser must refuse wrong sizes, invalidate past confirmations, produce a *real downloaded MKV*, and native independent `mkvmerge -J`, `mkvextract` and `ffprobe -show_packets -show_data_hash sha256` must prove original UID/track identity, exact original chapters/tags XML, still-targeted attachment bytes, exact replacement bytes and packet/timing identity.

The full Node/Vite/Chromium GitHub Actions check is a gating step. **Exact-head independent evidence satisfied for this tested layout.** No general consumer-player conformance claim follows from this single fixture and browser environment.

## Explicit non-claims and next structural block

This does not implement deleting/renaming attachments, adding to a source with existing Attachments master, changing FileData length, retargeting TagAttachmentUID, modifying Chapters/Tags, handling unknown EBML or CRC-protected files, large-file streaming, real device compatibility or guaranteed player conformance. It deliberately uses the previous research comparator's <=64 MiB coverage and the even lower product-only 60 MiB gate. No cross-session persistent File permission and no overwrite/rollback for an existing path.

The next P2 product class is an independent, reference-aware **variable-length / UID-graph** container writer with seek/cue/segment-offset and CRC rewriting proof, plus external MKVToolNix semantic extraction matrix. Do not mark P0 #77 universally resolved by this narrow byte-position-preserving operator.
