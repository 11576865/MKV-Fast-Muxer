# P0/P2-T — Source-bound final Attachments EBML resize with no Void

**Status: code, reviewed UI and independent E2E submitted; full exact-head CI PENDING.** This is a new bounded *real existing-container* writer class, not general Matroska structural rewriting or universal replacement of historical P0 issue #77.

## Source property that makes no-Void growth possible

The source must be a complete, finite-length Matroska Segment where **the very last Segment child is the sole Attachments master** and the selected target is **its final AttachedFile**, not targeted by any TagAttachmentUID. The source must have Tracks and Cluster, a readable complete original reference graph, known top-level EBML, no CRC inside the changed Attachments/AttachedFile and no Segment-level CRC. The original FileData SIZE and each enclosing master SIZE must have enough *existing encoded VINT width* to express the new value. Other element VINT widths and IDs cannot change.

An approved new FileData length changes `delta` bytes. The writer changes exactly the four existing **EBML size fields** for `FileData`, `AttachedFile`, `Attachments` and `Segment`, plus replaces the selected FileData payload with different-length bytes. It DOES NOT need any source-owned `Void`. Because the entire changed Attachments master was already last, no other top-level byte or SeekHead/Cues/Cluster/Chapter/Tag **position** changes. Other attached files precede the final AttachedFile, so their byte offsets stay unchanged; surviving metadata inside the last AttachedFile may move *within it* but must retain its UID/name/MIME/description and byte value. SeekHead referring to the Attachments master still points to the same original offset. No UID target is changed or retargeted.

The resulting output file and Segment lengths grow/shrink by exactly `delta`; that is a real parent-size structural change, in contrast to [same-size #136](https://github.com/11576865/MKV-Fast-Muxer/pull/136) or [reserved-Void #137](https://github.com/11576865/MKV-Fast-Muxer/pull/137).

## Safety and review

- Source 1–60 MiB, new single FileData 1 byte–4 MiB; only one finite Segment and final Attachments master accepted. No unknown top-level EBML, unknown size, multiple attachment masters, non-final target, incomplete UID target graph, duplicate FileUID, unsupported master children, CRC in affected Masters, VINT width exhaustion, or same-length requested change.
- The browser picks a **real source File**, target **actual UID** and replacement File. Referenced UID choices are visibly disabled. It requires an explicit checked risk review and source-current selection epoch, and verifies SHA-256 of both selected File inputs against the originally captured source immediately before execution and before manual download. A selection change invalidates the plan and download.
- A *genuine frozen plan* binds source and replacement File grants in a private WeakMap, never in JSON. The writer hashes complete source and replacement before/after, checks exact offsets/widths, then performs non-overlapping EBML size field patches plus one FileData splice to a **new Blob only**. No existing path can be overwritten; FFmpeg remux never serves as fallback.
- Independent local output reader must return the identical FileUID inventory and metadata, same unedited attachment FileData SHA, new target FileData SHA and same TagAttachmentUID edges. The raw full Segment inspector must show identical original EBML Header commitment, identical ID/order/start offsets of every original top-level child, and identical byte length/commitment for all **protected non-Attachments** top-level children, including original SeekHead/Cues/Cluster/Chapter/Tags. Segment header and final Attachments byte length must differ by exactly `delta`. Generic raw-preservation contract still does NOT grant generic writer permission.

## Independent real-container source and native oracle

Node positive cases create a small known EBML with ChapterUID nested atom and targeted Tag for a different attachment, and verify both growth and shrink. Negative cases reject TagAttachmentUID-targeted source, CRC, unknown Attachments child/top-level ID, Source not ending in Attachments, unknown Segment size, insufficient VINT width, same-size edit, review missing, cloned/forged plan.

The full browser E2E uses an **independently MKVToolNix/mkvpropedit-authored complex MKV** with two real attachments, a first FileUID targeted by Tags, an unreferenced final second, tracks/packets and nested Chapters. Because ordinary writer placement may not put Attachments last, a **test-only** controlled source transform replaces the old Attachments slot with an exactly equal-size Segment Void, appends its unmodified original master at EOF, grows Segment header size in its original encoded VINT width and repairs only SeekHead's original Attachments target SeekPosition to that appended location (without moving any original protected top-level element). The transformed source must first pass the project's raw/attachment inspectors and independent native `mkvmerge -J`, then the browser performs the actual *user-visible* no-Void resize. This is transparent: it does **not** claim all MKVToolNix files naturally use terminal Attachments. Any native validation failure means the feature is **not** accepted.

After browser manual download the independent native `mkvmerge -J`, `mkvextract` and `ffprobe -show_packets -show_data_hash sha256` must verify original TrackUID and other metadata, identical nested Chapters and targeted Tags XML, unchanged referenced original attachment FileData, exact new target FileData, all original compressed packet hashes/timestamps, source unchanged and correct file-size delta. A real 768px workbench screenshot is part of the browser evidence. The entire established browser/mux/batch/P0 test suite must pass on **the exact PR head** before marking ready/merging.

## Explicit non-claims

No general arbitrary-position Attachments relocation, shifting Chapters/Tags/Cluster/Cues, rewriting SeekHead/Cue positions, changing UID targets, CRC repair, unknown EBML preservation for modified masters, VINT width widening, other AttachedFile editing, >60 MiB streaming or cross-player guarantee. Those require a genuinely different source layout and further independent proof, not removal of this operator's refusal gates. Do not treat a passing synthetic Node fixture as equivalent to native output acceptance.
