# P1 ContainerProject 草稿回读与来源重核：独立工程切片

日期：2026-10-13
基线：已合并的五步预览 PR #120（main \`31af804e5f60ec0da0f8dccf70e11e2551b7e591\`）

## 范围

- 用户从真实组成面板导出版本化 JSON，随后使用“检查工程草稿”重新导入；
- 严格解析最多 1 MiB 的 \`container-project-v1\`；不允许未知字段、历史 writer 授权、已有文件句柄、内部验证结果或伪造的可执行状态；复用领域构造器的对象身份、类型与来源引用校验；
- 在当前可见的 \`ContainerDocument\` 来源和组成上对照导入草稿的对象 ID，报告仍在、消失、新增的数量；
- 即使显示 ID 和来源名完全匹配，仍标为 \`display-identity-only\`：**文件名/大小/时间不是可靠字节身份证明**；未经过真实媒体读取与完整独立验证，不会从导入获取 writer 权限；
- 检查流程不调用封装器、不改写 \`FileList\`、不修改现有容器、配对或执行任务；恶意/旧版草稿拒绝并明确显示原因。
- E2E 使用 PR #120 的真正从 Chromium 导出的 JSON 下载，重新导入，并用带 \`writerStatus:verified\` 的伪造版本做负例；另有纯 Node 领域测试。

## 退出条件

准确提交必须 Node 全绿、构建全绿、完整 Chromium E2E 通过，且此前 P0/P2/P3 成品安全门禁保持原样。PR 合并后复验主干。

## 不属于本轮解决的问题

仍没有真正的 \`ContainerProject\` 可写单一权威、来源全字节 hash 绑定、编辑器字段的事务恢复、权限恢复、OPFS 持久化或可执行后端。这条切片只完成安全数据输入与变化审查，不能被宣传为理论 P1 已封板。

## P1 后续：有界、完整来源字节摘要（2026-10-14，PR #122）

此前仅靠文件名、大小、修改时间与对象 ID 的“显示身份”不能证明来源字节一致。新增 `ContainerProject v1` 可选 `sources[].sha256`；当用户导出实际已选媒体且文件不超过 **64 MiB** 时，浏览器通过 WebCrypto 对**完整文件内容**计算 SHA-256 并保存到不可执行的工程草稿。导入旧草稿仍可审查，但无摘要时不可声称完成字节级重新关联。

导入新草稿后，用户可**显式**点击“核对已导入草稿与当前媒体的完整 SHA-256”，对当前重新选择的 File 再次完整求哈希，并与 JSON 中的摘要比较。每次异步计算必须验证当前 File 对象以及导入草稿的引用没有更换；两个耗费内存的哈希操作均应防止同一动作重复执行。文件超过 64 MiB 时直接拒绝完整哈希，不得转为抽样前缀或未经证明的“哈希已验证”。

**信任边界**：SHA-256 是与*用户所提供 JSON 里声明的摘要*进行比较。JSON 可自行编辑，不带签名，因此摘要相等既不能证明草稿作者、时间和已编辑数据未被伪造，也不能证明章/轨对象语义没有漂移。即便摘要相等，`executionAuthorized=false`、`changesApplied=false`；不得静默恢复任意旧编辑、授权浏览器文件写入或宣称全部 Matroska 结构保真。64 MiB 是当前 `crypto.subtle.digest` 一次性全文件内存策略的明确限制，而非 Web/Matroska 理论上限。

本条是 P1 **来源字节验证切片**，并非完成通用流式哈希、项目权限迁移或正式 P0–P6 退出门槛。
