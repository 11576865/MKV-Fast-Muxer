## 0. 版本权威及历史名词更正

用户确认：曾经称作“软封10.14版本”的产品实际应称作**“软封0.1014版本”**。历史标题、CSS 文件名、JS 常量标识 `sf14` / `SOFTMUX_1014_*`、测试名及 Figma 历史引用只作为技术身份/追溯索引，并不是对错误产品版本的重新确认。该历史阶段用户可见版本应为“软封0.1014版本”；后续版本依照增量发布继续推进。

本合同中的**“1.0版本”是未来正式产品发布名，不是本合同签署时的当前发布状态**。2026-10-12 战略决议文件自己的“版本：1.0”属于**决议文档的版本号**，不能推导软件已经是 1.0。

**版本管理增补（用户 2026-10-16 指定）**：每次形成可交付软件更新，产品版本随更新递增，不再长期沿用旧号。自本次 0.1015 起，`package.json.version` 为 `0.1015.0`（npm 三段格式），界面显示 `软封0.1015版本`，封装报告 `application.version` 使用相同的 `0.1015.0`。代码共用 `src/product-version.js`，并以测试防止分裂；下次功能更新须再次递增版本。旧 `1.2.2` 属于历史清单值，不能再用来标记当前交付。**1.0 发布仍须完成 manifest、UI、报告与实际部署的严格核对。**

用户决定：**在达到 1.0 退出门槛以前，不要求其继续将开发中版本作为正式日常使用产品**。可以持续进行开发、真实测试与受控评审，不得把阶段性 PR/CI 绿色宣布为 1.0 发布。

## 1. 不可变产品目标

- 领域中心是单一语义上的 **Matroska 拟输出容器工程**；视频轨不是所有合法工程的必需根节点。轨道、附件、章节、标签、来源和目标均应是一等对象。不能因规范允许而虚构现有写入能力。
- 字幕 / 字体交付仍是旗舰工作流；旧单工程快速封装、批量字幕交付能力必须保留（L-001—L-044 逐项验收）。
- 对象中心工作台：目标容器/任务矩阵 + 当前对象 Inspector + 按需来源与专业操作；禁止把内部 EBML/执行阶段当作各自的主页面。
- 计划、预检、执行、成品生成、原生结构核验、隔离字体渲染、实际持久保存和播放器表现必须保持不同证据状态。没有事实来源的通过结论一律不显示。
- 浏览器本地处理，兼顾桌面和平板。对不安全写入、身份漂移、权限失效、未知 EBML 与相互冲突的修改执行明确阻断。
- 本项目不承担完整 ASS 创作器、字体二进制编辑器、视频剪辑/硬字幕压制、万能转码器或万能 EBML 写入器。

优先级：**数据不破坏 > 功能继承 > 输出正确性 > 清晰交互 > 增强功能数量 > 视觉装饰**。

## 2. 联合开发原则：每个增量必须同时处理 UI 与工程语义

不按“先全部 UI，再做后端”或“后端完成之后随手加按钮”的孤立流水线推进。每个纵向切片至少需要：
1. 用户任务及对象身份（是谁的资源/轨道、谁拥有状态）；
2. 能力解析：可用、只读、受限、计划、阻断；
3. 界面操作与交互反馈：选中、编辑、撤销、错误、帮助、输出影响；
4. 领域事务或执行器接线：只能使用真正可证明的实现，不得复制第二套可写状态；
5. Node 单元测试 + Chromium 任务路径 + 适用时原生 MKVToolNix/ffprobe/CRC/字节证明 + 真实浏览器截图；
6. 保持撤销/恢复/旧入口与当前用户数据完整性的回归。

功能尚未完成时可保留**正确上下文中的入口**，但必须显示受限理由，不允许伪造提交或输出成功。

## 3. 联合收敛路线与退出门槛

### R0：当前版本更正与双线基线
- 0.1014 历史版本已经更正；当前开发版继续递增至 0.1015，技术历史标识可暂时不动。
- 冻结并标记现有 `main`、完成的旧功能证据和 Figma 原型；建立用户工作流—对象—命令—执行证据追溯。
- 不变更 `main` 的生产发布，只从独立 1.0 开发分支/PR 起步。

### R1：真正的拟输出对象中心
- 单工程不再只有轨道可以作为主操作对象。附件、章节、标签必须展示**来自实际来源扫描**的列表、详情、引用证据及受限/支持状态；无真实来源时显示“未扫描”，不可凭空生成对象。
- 使用现有真实来源 Inspector/编辑事务，不复制轨道、附件或来源写入状态。
- 已支持的附件选择、保留/排除/名称/MIME、提取与受限替换归入正确上下文；章节/标签的只读观察与可写条件严格区分。
- 退出：复杂 MKV、无来源和多附件场景中，用户可以准确发现对象、定位来源、知道可执行范围；没有“只有说明文字”的假工作页签。

### R2：ContainerProject 单一语义编辑模型
- 收敛来源轨道、外部音视频/字幕、附件、章节、标签的身份、provenance、变更意图、冲突检查与 Undo/Redo；旧 FFmpeg 适配层作为临时消费者，而非第二个隐式事实来源。
- 工程草稿序列化/恢复须经过文件字节核验、重新授权、版本迁移及明确同意；不得用文件名大小相同冒充来源身份。
- 退出：至少覆盖典型混合对象工程的真实交互事务与回放、撤销、执行计划一致性，异常不得静默覆盖用户修改。

### R3：受约束的安全 Matroska 执行
- 保留现有 stream copy / libass / FFprobe / 附件替换等已验收技术；实现所需安全写入扩大覆盖，但**1.0 并不表示支持任意 EBML 改写**。
- 必须明确无修改往返、复杂嵌套章节与定向标签保留、UID / CRC / SeekHead / Cues、未知结构的“不改变/可验证改变/阻断”边界。
- 对无视频、附件-only、复杂章节/标签编辑分别给出“真正可执行并独立验证”或“明确不可执行”结论，不能把实验性写入当作正式支持。
- 退出：至少一组独立生成的复杂源 MKV 成品通过原生结构/字节证据检查；不支持类型 fail-closed。

### R4：批量与成果生命周期
- 配方 → JobMatrix → 单任务 Inspector → 执行/取消/重试 → 实际成品审计/保存，遵循单项身份；旧批量功能回归。
- 测试实际不少于 20 个输出任务的长批次，不以纯配对计划代替封装；包含权限丢失、输出冲突、中断和不完整保存。
- 退出：批次输出/报告与单任务身份一致，取消与失败不损毁已完成成果、旧 Blob 生命周期可解释且无虚构“已保存”。

### R5：可信交付证据
- 将拟输出预检、真实 Matroska 结构、码流复制、字体闭包、最终 MKV 隔离 libass 渲染和目标播放器实测分别标注、保存证据。
- 当前不可能验证的播放器环境必须显示“未测试”；无证据不能宣称“跨播放器完全兼容”。
- 退出：对旗舰 ASS/字体交付样例，包含最终成品而非单纯来源预览的独立验证；有清晰可导出的报告/失败原因。

### R6：1.0 发布验收
- L-001—L-044 无声丢失项数为 0；每项有可发现入口或标注支持边界、实际验证结果及必要的迁移说明。
- 桌面/平板真实 Chromium 任务截图、交互和焦点/草稿保持验收；至少开展真实平板触控和目标浏览器测试，检查可用性、密度与低眩光对比度。
- 精确目标 commit 上 Node/build/Chromium/独立 Matroska 工具与实文件证据全部通过，包含失败反例。
- 明确 1.0 产品标识与版本 manifest/报告 schema 的映射，产物与正式网站部署核对，并具备回滚策略。
- 只在所有已承诺范围满足退出门槛、没有未解释的高风险数据破坏路径时，对用户声明**软封1.0版本**正式可投入实际使用。

## 4. 发布规则与当前状态

当前 **R0 开始**；R1—R6 均不得从“绘制 Figma 图 / 存在按钮 / 单测通过”自动推定完成。UI 与后端每完成一个纵向任务一起验收；遇到设计与执行器冲突时明确记录而不擅自缩减已批准的功能。

**在确认 1.0 发布之前，保留稳定分支/回滚途径；开发分支、测试工具与已生成的实验性输出只供验收使用，不要求用户继续日常使用 0.1014。**
