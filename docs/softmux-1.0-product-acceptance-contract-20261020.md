## 1. 一句话产品定义（可反证）

软封1.0 是 **桌面与平板 Chromium 浏览器中、本地离线处理资源的 Matroska 工作台**：一个用户能够在「单工程」导入实际来源、查看真实轨道/附件/章节/标签、组织输出轨道与外部字幕/音频/字体、检查受支持的元数据/附件操作、预览、审核输出计划、执行 Stream Copy MKV、独立核验并保存结果；在「批量任务」审核多项输出并顺序执行、失败重试与独立保存。

**它不是**任意 EBML 结构编辑器、完整播放器/ASS 制作器、任意浏览器或平台无条件支持、后台持久执行系统。完整/受限/阻断三种能力状态与“已规划”分开显示。**不接受只有 UI、只有逻辑测试、只有 ffmpeg 返回 0 而没有真实成品的验收**。

## 2. 首发界面：用户必须找到什么

| 入口 | 用户必须能完成的操作 | 退出条件 |
| --- | --- | --- |
| **单工程 → 来源 / 导入** | 加载现有 MKV 或已支持的外部媒体、导入字幕/音频/字体；按真实扫描结果显示轨道、附件、章节、标签、来源名称和身份 | 不以文件扩展名或伪造对象替代实际扫描；同名不同文件不可继承原编辑权限 |
| **单工程 → 拟输出组成** | 对已支持的轨道与附件选择保留/排除、添加外部字幕/音频/字体、设置已实现的语言/标题/默认/强制等属性，显示最终拟输出顺序及变更影响 | 控件对执行器有真实作用；无能力时显示「只读/受限/不可执行」原因 |
| **单工程 → 当前对象检查器** | 选择具体 Track/Attachment/Chapter/Tag，查看来源信息、字段和操作；章节/标签至少只读检查；受支持的附件/元数据可进入已有严格 writer | 不产生第二个独立的、未与工程绑定的“假可写”对象；切换视图不丢失草稿 |
| **单工程 → 预览/预检/交付** | 生成已支持的 ASS/libass 静态预览；查看封装计划；启动/取消任务；读取真正的输出 MKV、导出报告并保存成品 | 预检 ≠ 成功生成 ≠ 独立验证 ≠ 已保存 ≠ 已在播放器确认 |
| **批量任务** | 根据已支持的文件名配对/Recipe v2 生成任务矩阵，检查单项映射/冲突/字幕/字体选择，顺序执行、取消、失败重试、保存与导出每项结果 | 不通过重复驱动主工作台按钮制造状态串扰；结果与唯一任务 ID 对应 |
| **容器工具** | 对已有 MKV 进行独立结构观察、提取和受限安全编辑 | 所有操作显示明示约束、最终生成独立新副本，不能覆盖来源 |

UI 可以复用现有 DOM/入口，不规定重建 UI。功能入口存在但不可执行，不等于已达标。

## 3. 二值发布验收项（每一项都是 MUST，不能由界面截图取代）

| ID | 用户场景与输入 | 必须观察到的结果 / 失败即不满足 1.0 |
| --- | --- | --- |
| **S01 实际来源** | 导入一份含视频、至少两条音轨、来源字幕、附件、章节/标签的真实 MKV；另导入外部 ASS 与字体 | 来源、拟输出对象准确枚举；未扫描/对象缺失有明确状态；切换来源后旧 File 身份和草稿不会错误附着。输出计划只引用新来源。 |
| **S02 普通软封** | 选择有效 MKV 或现有已支持外部视频、加入一条或多条 ASS/SSA/SRT/WebVTT 及所需字体，配置轨道保留/排除、语言/标题/Default/Forced | 真实产生 MKV；预期视频/音频未重新编码；独立检查实际轨道清单、流内容/时间轴、字幕和附件符合用户选择；来源文件无改写。图形字幕 PGS/VobSub 使用单独有效夹具进行旧功能回归。 |
| **S03 字幕字体** | 用包含复杂 ASS、至少一个目标字体与一条故意缺字/缺字体反例的项目执行预检、预览、封装、成品读取 | 能看到预览与字体诊断；字体附着按保留/子集策略实际出现在输出；独立提取并按字节/字体身份检查，目标 ASS 样例用成品来源与隔离 libass 做抽样渲染。不宣称所有播放器视觉一致。 |
| **S04 轨道属性** | 对来源音频/字幕执行保留/排除、已支持的同类型排列、标题/语言/Default/Forced 修改，必要时额外导入音轨 | 输出 MKV 中轨道数、顺序及可表达的属性与冻结计划一致；未获执行能力的属性明确阻断，不允许只改 UI 文本不改成品。 |
| **S05 附件管理** | 输入拥有至少两个字体附件的 MKV，保留其中一个、排除一个，并添加一个外部字体；对支持字段尝试重命名/MIME 变更 | 目标容器的附件清单、文件数据、保留/排除状态与计划一致，经 ffprobe + 独立 FileData SHA-256/原生读取核对。对于保真受限的原 MKV，必须事前拒绝，而非静默丢 Chapter/Tag。 |
| **S06 有界原位编辑** | 使用满足当前 writer 布局的来源，执行一次受限附件 `FileData` 替换；使用未知结构/TagAttachmentUID 引用、超预算、CRC 错误等负例 | 正例生成与原文件分离的 MKV，并独立验证不相关原始顶层字节、其他附件、UID/Tag 引用不变；负例明确拒绝、来源字节未变。**现有独立 writer 的 60 MiB 来源及 64 MiB raw research 上限可保留为 1.0 特定能力边界**，不得冒充全体 MKV 1 GB 可写。 |
| **S07 章节和标签** | 对真实来源扫描章节/标签；在独立可验证样本中对 `ChapString/TagString` 作相同 UTF-8 字节长度替换；另使用不等长/未知 UID 关系来源 | 实际列表与所见文件相符；受限正例产生独立可回读文件；不等长或无能力负例拒绝。**不以任意章节树重建、增删、任意变长作为 1.0 必需支持项**。观察结果不得自动授予写入权限。 |
| **S08 容器保真失败封闭** | 使用 Issue #77 类含嵌套章节与指向章节的 Tag 的复杂来源，尝试有风险的普通 remux 或修改 | 要么采用经独立证明没有损失的可执行路径，要么在开始写出正式成果之前清晰阻断；不得生成成功报告却遗失嵌套 `ChapterUID` / 定向标签。 |
| **S09 工程草稿与撤销** | 在有真实来源的单工程修改轨道/附件/外部资源的已支持字段，执行撤销/重做；导出工程草稿，刷新页面后重新导入并重新选择来源 | 在支持范围内，草稿能被明确恢复到同一可执行计划；身份或旧值冲突必须拒绝且不修改现有草稿；不自动恢复浏览器 File 权限，也不自动执行封装。不支持恢复的编辑类型必须显式列出，而非显示「完整工程已恢复」。 |
| **S10 批量 20 成品** | 用真实媒体来源创建至少 20 个任务，包含不同字幕配对、共享/单集字体；另设置不合法配对、任务失败及保存失败场景 | 至少 20 个实际执行的任务结果（非仅有计划行），逐项可独立回读；成功项不因后续失败而丢失；冻结任务可重试失败项，已生成但仅保存失败的文件可以只重试保存，不重新 mux；单工程草稿不受批次串扰；消除已复现的 SRT 时间轴偏移缺陷。 |
| **S11 成品/保存收据** | 任一 S02/S05/S10 成功任务，先生成再尝试下载和（支持 API 时）目录保存；模拟权限失效和名称冲突 | 准确区分计划、已生成、已审计、待保存、保存成功、保存失败；真实成功时才出现 `saved`。失败时保留有效已生成成品及可解释的恢复入口。输出报告记录实际版本、来源与本任务成品身份。 |
| **S12 约 1 GB 执行包络** | 桌面 Chromium 与明确登记型号/OS/浏览器版本/可用内存的目标平板，各运行 MKV 主来源分档 **256 MiB、512 MiB、768 MiB、1,000,000,000 B 左右**的真实封装，包含字幕/字体和保存 | 每个已宣称支持的规模均实际成功封装、回读与持久保存，无标签页崩溃/静默损坏/来源覆盖，并记录峰值内存、耗时、输出字节及独立媒体核验；失败即该环境包络尚未验收。**首期具体目标：单个来源 MKV ≤1,000,000,000 B；单个输出 MKV 也在已测试的 ≤1,000,000,000 B 预算内。** 来源与新增附件导致输出超预算时须明确拒绝/终止，不误报成功。该大小边界是目标，现行 main 未获证明。 |
| **S13 实际工作台** | 目标桌面 Chromium / 平板实际访问主工作台，完成 S01→S02→S11、S10 任务；测试键鼠与平板触控、窗口窄宽变化、滚动、弹层、任务切换 | 输入控件、对象列表、检查器、计划、保存、错误/撤销入口可达；切换章节/标签/附件观察不丢失已导入来源或有效编辑；文件选择控件清空不代表来源权威丢失。浏览器 E2E + 真实设备证据均存在。 |
| **S14 发布与回归** | 指定一个拟发布 commit 和对应网站构建 | 在该精确 SHA 完成 Node/build/Chromium、适用原生 `ffprobe/mkvmerge/mkvextract` 成品检查；44 旧能力逐项以保留/范围受限/经用户授权延期和证据说明对账；57 原始场景逐项记录与首发范围的映射、已验证/未验证证据，首发 MUST 项不能只停留 `partial/unassessed`。版本/UI/报告/部署一致；网站实际访问和回滚路径检查通过。 |

### 验收裁决规则

- `PASS`：有指定精确 commit、测试来源、浏览器/系统/运行时、真实输出及独立校验的对应证据；适用的 UI 任务与保存状态均成立。
- `FAIL`：承诺的路径存在反例、来源发生意外改动、成品与计划不符、状态丢失、未处理的高风险结构损失。
- `BLOCKED`：设备/权限/基准文件不可得；不得因为没有测试而认为通过。
- `OUT_OF_SCOPE`：此版本明确不承诺，产品必须展示限制/拒绝路径；不是 PASS 的替代品。
- `IMPLEMENTED_NOT_ACCEPTED`：源代码或独立单测存在但缺完整用户任务/成品/设备证据，不得纳入已验证的 1.0 完成数。
- 对每个 S01—S14 应挂接当前主干 PR/模块/E2E/人工证据、最后执行 SHA、最终裁决；禁止用一次 PR 合并直接批量晋级所有案例。

## 4. 明确不在 1.0 范围（不是等待它们完成才可以发 1.0）

| ID | 不交付的能力 | 1.0 对应行为 |
| --- | --- | --- |
| N01 | 任意未知 EBML/CRC/UID/SeekHead/Cues 结构编辑、任意 MKV 完整无损 remux | 安全能力判定与保真风险阻断；已有受限 Writer 可用 |
| N02 | 普遍增删章节、任意变长标题/Tag、结构重排与自定义 UID 图编辑 | 实际扫描、只读检查 + 已验证等字节长度修改 |
| N03 | 通用附件-only Matroska 或所有无视频类型的正式可写交付 | 工程模型可表达，读取/检查按可用能力执行；仅实际验证的子类型可写，其他标注实验/不可执行 |
| N04 | 全浏览器/移动系统同等功能、用户关闭页面后任务仍运行、任意大文件 | 公布经过实测的桌面/平板 Chromium 环境及 ≤1 GB 已验证工作流，允许支持环境外明确拒绝 |
| N05 | 批量并发多个 FFmpeg、断点续封整部 MKV、无需重新授权恢复本地文件句柄 | 单重型任务顺序执行；计划/已完成成果可追踪，未完成任务重新执行 |
| N06 | 完整 ASS 创作、字体二进制编辑、烧录硬字幕、泛转码、视频剪辑或全播放器兼容性保证 | 保留本项目专业软封装和验证职能，报告对实际播放器测试范围如实标注 |

**注意**：N01—N06 不意味着已存在的旧功能可以任意删除；旧功能 `L-001—L-044` 的意外损失仍属回归缺陷。本文未批准任何已存在核心能力的删除。

## 5. 不能只用「几天/几周」代替产品完成标准

开发候选版可以以约 **3—6 个有效开发日**为冲刺规划假设，**但这并非正式发布工期证明**；也不把此前 5—8 周的拍脑袋式估计保留为发布承诺。首先确认 1 GB 真实执行包络，再以 S01—S14 的未通过项数量及阻断性质决定是否发布。

1. 先量出已有功能能完成哪些 S01—S14；已有代码、已通过的 Node、已有 Chromium 和原生验证直接复用。
2. 排除 PR #159 中与主导入控件预期清空行为相矛盾的断言，并改测来源权威/工程草稿身份。
3. 只修确证失败的项目：统一交互、冻结计划、批量重试、安全 writer 接线、1 GB 缓冲、发布验证。
4. **不为 S01—S14 新造并行领域状态或通用 EBML writer**，除非具体场景证明已有实现不可复用。
5. 用户批准本表后，1.0 首发新增功能以 S01—S14 为目标；任何额外功能必须通过显式范围变更，不得无限扩张标准。

## 6. 待用户确认的具体发布取舍（不可偷偷当作已批准）

- 单个 MKV 1 GB 是只限制 **来源大小**，还是 **来源与生成结果均 ≤1 GB**？本文暂按更保守的后者拟定，但用户当前只明确过约 1 GB 的 MKV 限制方向；这需要进一步确认。
- 是否将非典型无视频容器的 **写出**纳入 1.0？当前方案建议仅保证模型/检查与已有经验证子类型，附件-only 的普适创建延期。
- 是否接受复杂章节/Tag 场景中 **只读+拒绝不安全修改**作为 1.0 正式可用能力？这是已批准方案 B 的合理解释，具体范围仍需在此表核定。
- 正式支持的 Chromium 桌面和平板 **参考硬件、OS、浏览器版本、至少一种保存方式**应在 S12/S13 首次真实测试后锁定，不能仅写「现代浏览器」。
- 最终是否要求 **20 个真实封装任务**都成功，还是要求至少 20 次任务执行且合理包含预期失败/保存失败、成功项完好？当前 S10 采取后者并分别验证成功与失败，不能用计划任务冒充真实执行。
