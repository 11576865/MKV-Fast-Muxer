# P1: Semantic audit of actual browser-produced MKV with declared attachment additions

Date: 2026-11-03. **Proposal under implementation; independent exact-head CI required.** No changes to production mux, browser writer permission, ordinary output reports or formal 1.0 release contract.

## User-value connection

A Matroska writer may legitimately add the one or two generic attachments requested by a user. The earlier independent P1 UID-role oracle (#229) compares unmodified source/output roles and would therefore label this intended change a difference. The existing P2-A browser test already verifies individual payloads, unchanged raw Chapters/Tags XML and ffprobe packet facts, but does not bring those checks together as one **source + explicitly authorized changes = actual output** receipt.

This PR wires the P1 role-resolved oracle to the **actual browser-downloaded MKV** produced by the existing P2-A Chromium scenario, under a deliberately narrow contract: attachments added, no other edit authorized.

## Exact user intent, not a self-asserted output manifest

During the browser scenario, the source is an independent MKVToolNix-authored real MKV with nested ChapterAtom and targeted Tag. The test passes actual bytes to the workbench's one-/two-attachment writer and downloads the real MKV.

The test independently derives a manifest for each output using:
- SHA-256 of the exact unchanged source file;
- SHA-256 of the exact downloaded browser output (binds audit to that artifact, not the UI's report text);
- attached source input Blob bytes, intended filename and MIME selected before output.

No output file attachment inventory is trusted when authoring expected additions.

`scripts/p1-browser-delivery-semantic-audit.py` validates manifest schema and file identity, independently runs native `mkvmerge` and `mkvextract` over source/output, and accepts **only** explicitly declared new attachments; it also requires unchanged original attachment hashes, ordered track type/codec, complete extracted chapter/Tag tree with resolved known UID targets, and identical independently observed ffprobe packet SHA/PTS/DTS/duration/size rows.

Three real-file cases form the CI gate:
1. One browser-created `readme.txt` attachment, correct source and output;
2. Two browser-created attachments, including user-edited filename/MIME, correct source and output;
3. Same real browser MKV with a deliberately wrong approved FileData SHA: **must** return `DIFFERENCE_DETECTED` instead of PASS.

```bash
# Generated by the existing Chromium E2E fixture scenario:
python3 scripts/p1-browser-delivery-semantic-audit.py \
  .e2e/output/limited-existing-source.mkv \
  .e2e/output/limited-existing-browser-result.mkv \
  .e2e/output/p1-browser-single-expected.json \
  .e2e/output/p1-browser-single-semantic-audit.json

npm test
```

The result is persisted as a JSON report, with the source/output MKVs and intentionally incorrect manifest downloadable as CI evidence.

## Boundaries and technical controls

- P1 verification is **independent native CI**, not a browser user's runtime capability; no Python/MKVToolNix requirement is added to the product.
- The comparer does not authorize general attachment replacement, arbitrary source/object editing, changes to chapter or Tag bodies, or additional tracks.
- Matching UID roles only covers the existing P1 supported roles; track identity by type/codec/ordinal is strengthened for this test with ffprobe compressed-packet hash and timestamps but does not establish all format or playback semantics.
- Unknown non-extracted EBML, detailed per-track metadata beyond the named fields, font rendering, cross-device limits, and user's actual disk persistence are outside this receipt.
- The blob manifest is an independent test intent; a production user-edit intent contract requires separate integration work. This PR intentionally avoids inventing a duplicate UI report or presenting native CI evidence as verified browser capability.
- A failed command, missing downloaded MKV, invalid declaration, missing UID target or unexpected attachment fails without a positive certification.

## Acceptance criteria

- Exact-head Node test, build and actual Chromium output flow pass.
- Native P1 audit PASS on one/two real browser MKV artifacts.
- Wrong SHA negative returns code 2 and explicit attachment difference.
- CI uploads all input/output MKVs, expectations and reports.
- Existing P2-A and S01–S14 behavior not changed and legacy paths remain intact.

**Do not declare accepted before exact-head workflow evidence.**
