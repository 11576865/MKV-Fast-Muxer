## 1. 修复的问题：真实对象编辑器仍被列表挤到下面

上一轮撤掉 8 个永久阶段导航和 3 个复制状态栏，620px 的任务矩阵从 y≈746 恢复到 y≈250，桌面从 y≈370 恢复到 y≈200；但对照真实 Chromium 820×1180 截图发现：

- `#batchPlan` 与 `#batchJobInspector` 在宽度 820px 仍然上下堆叠。
- 用户选定原生任务后，字幕标题/语言编辑器出现在任务列表下面，不在任务行的直接视觉关联位置。
- 只用两个任务的展示图片不足以证明 10—20 条任务时仍能快速找到并编辑选中对象。
- 620px 不具备物理并排空间，不应强行缩小字段宽度以伪造桌面视图；但点击任务后必须能抵达它的**同一原生检查器**，不能重新生成第二套“快捷编辑器”。

## 2. 实际修改与边界

`src/softmux-v3.css` 的 V3.5 opt-in 限定：

- `780px <= width <= 1180px`：`.batch-review-layout` 显示真正的双栏 *master–detail*；列表至少 285px，检查器至少 360px。长任务列表仅在原生 `#batchPlan` 内进行有界滚动（最大 600px / 53dvh）；检查器保持真正的原生控件，未复制 File、字幕元数据、执行状态或新的任务模型。
- `width < 780px`：保留纵向主从视图。用户真实点击 `button[data-batch-job-index]` 后，原 `src/main.js` 先确定 `selectedBatchVideoFile` 并渲染 `#batchJobInspector`，V3.5 仅在下一帧把 `#sf14Batch` **局部滚动**到这一原生检查器，聚焦其既有区域而不提交字段或触发运行。点击 `input[data-batch-execute-index]` 不会跳转；两者必须保持不同的操作语义。
- 桌面仍保留完整来源栏和原生矩阵/检查器，不增加另一排导航；平板/窄屏仅有之前已经恢复的两个原生披露入口。
- 实际执行器、来源与输出权限、任务选择、原批量运行记录、结果审计、默认 V3 及既有 Figma 设计文件均不改。

## 3. 真实浏览器覆盖

独立 `tests/e2e/v35-batch-many-job-density.e2e.mjs`：

- 通过 FFmpeg 产生一份可解码短 MP4，复制成 16 份**文件身份和名称各自独立**的 MP4；16 条命名明确的真实 SRT 提供对应任务。重复媒体**字节**只用于实际导入与密度/匹配测试，不计作 16 次真实编码器产物验收。
- 导入 32 份真实 `File`，要求 16 个原生 `data-batch-job-index` 且 0 歧义、1 个原生 `#batchJobInspector`，无 8-stage shell，执行与编辑输入节点不复制。
- 1440px 验证 desktop 原生列表/检查器仍并排；820px 验证检查器与列表有相近的实际顶边，并在第一视口可见原生字幕字段，长列表在内部滚动，操作后仍保持主从关联。
- 620px 验证默认队列位于首屏；点击第 14 条原生任务自动将现有检查器对齐原生批量窗格顶部，保持外部标题栏和 11 个全局入口固定，不替换目标 File。用户实际编辑字幕标题，切换到另一任务再回来，改动必须保留。
- 所有视口上传真实全尺寸 Chromium PNG 和包含原始元素几何尺寸的 JSON receipt；要求通过真正的 DOM hit-test/focus/field mutation，不以静态 Figma 图、单纯截图数量或独立任务伪造结果。
- 另有 `tests/e2e/v35-batch-deep-workflow.e2e.mjs` 继续对两个真实视频/两条字幕执行实际配对歧义→人工确认→修改字段→只封装 B→下载并独立 FFprobe/FFmpeg、SHA-256 验证；**16 条任务专项不声称已经执行 16 个 MKV**。
