## 3. 真正需要先解决的 P0（初版交付阻断）

### P0-A：让拟输出内容重新成为主界面

**现场证据：** `plan-1440x900.png`、`plan-820x1180.png`、`compact-target-figma-vs-browser.png`。现状在拟输出标题后突出“工程草稿·核验与恢复”和大块“基础容器附加结构”（章节、标签等只读观察），主要视频/音频/字幕编排行较晚才进入可视范围；批准的 V3-04/V3-06/V3-08 首屏以轨道组合为主体。

**唯一工作目标：** 重排主工作区的 **信息架构**，不改媒体引擎、字段所有者或字体闭包逻辑。拟输出名/状态 → 视频/音频/字幕的真实可选组合行 → 次要资源/章节标签与高级工程选项；辅助结构可以折叠，但必须可达，不可直接删功能。保留真实 `#compositionTracks`、`#workspaceHistoryPanel`、`#outputEvidencePanel` 等唯一节点和原有事件。

**退出标准：** 1440×900、1180×820、820×1180、620×900 的真实 MKV 拟输出截图均把至少一个主要组合轨道置于明显的主内容区，章节/标签和工程审计不抢占首要操作位；选中轨道和 mux/download 仍可完成；没有克隆的编辑器、丢失的 File 或凭空声明的输出保真。

### P0-B：验证正式空态的实际载入行为

**现场证据：** V3-10 的原生输入与原 dropzone 被复用，WU-01 测试只确认原节点存在，并通过 Playwright `setInputFiles` 直接注入文件；**不能把它算作**“用户直接点击空白容器 / drag-drop 均已测试”的证据。

**退出标准：** 用真实 Chromium 模拟用户点击空态的可点击区域并验证打开唯一原生 file chooser；使用实际 `DataTransfer`/drop 事件送入真实 MKV，核对来源扫描、File 实例连续性、单入口与没有默认拟输出。不要新建平行 uploader。

### P0-C：当前 HEAD 的回归闭环

**现场证据：** `411168923` 四个工作流审查时均 queued；前一 `cc0c432` 绿色不能替代。

**退出标准：** 最终候选提交 SHA 的 Node/build、V3 Chromium、完整 Browser E2E、S12 全部得出可核验结论；若失败，按阻断影响修复，避免继续新增与产品交付无关的专项测试。提交前后需记录与 `main`/PR #233 的重叠代码合并债务。最新仓库文档和实际 PR HEAD 一致。
