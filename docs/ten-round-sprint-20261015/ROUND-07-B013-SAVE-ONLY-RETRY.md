# Round 7 · B-013 仅重试保存（2026-10-15）

实现原理论模型 B-013：目录保存失败时，重新保存已有完整成品，而非再次生成/封装。继承 R6 repair head `b2928791b054689204a9cbafc5e909efca52cb62` 的相同代码树；R6 全 Chromium/native CI 尚待验收，单独保留其状态，不阻断这一独立保存切片。没有声称 Round7 全部 20 集/恢复/性能要求已经完成。

## 产品行为

- 完成的批次结果行提供“仅重试保存”。保存的是会话中已生成的原 MKV Blob 与原报告 Blob，不读取素材、不调用封装器、不重新审计。
- `createBatchSaveRetryRegistry` 私有保存每个 Job 的冻结产物与目录范围内的 MKV/报告保存凭据；结果行可写状态不能伪造成品字节身份。
- 同目录（包括 `isSameEntry` 确认的新句柄）再次保存，只尝试缺失的文件。对已提交文件重新流式核对 size/SHA-256：原 MKV SHA 对实际产物，已保存报告对保留的报告字节。
- 失败残留、原文件被改动、大小写/Unicode 规范化同名文件、权限错误会阻断重试。不覆写、不删目录文件，不把残留空文件当作可以任意清除的数据。用户可检查并手工处理，或选择新目录保存完整文件对。
- MKV 保存成功而报告仍失败时保留部分成功凭据；重试保存不能将未通过的独立审计变为 pass。任务状态仅允许 saveWarning/awaitingSave/auditWarning -> saving -> 相应终态，禁止返回 muxing/preparing。
- 重试期间串行锁定；新批次真正启动时同时释放旧保存字节授权与旧下载 URL。选择新素材或修改配方不改变之前保留的成品。此授权不会进入配方/JSON，也不承诺刷新后仍能恢复 Blob。
- 验证/冲突检查与写入之间没有跨进程原子锁；保留既有 File System Access 的 best-effort 不覆写边界，不宣称解决所有外部进程竞态。
