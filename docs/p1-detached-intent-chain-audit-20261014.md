# P1：导入工程草稿的修改记录内部一致性（非回放）

日期：2026-10-14
范围：继 PR #120（工程草稿）、#121（严格导入与对象比较）、#122（受限来源字节 SHA-256）之后，防止**自相矛盾的修改记录**通过导入。

## 现有漏洞与修正

此前 `parseContainerProjectDraft()` 检查 schema、revision 范围、对象存在性、基础值类型，但未证明修改记录的内部状态连续，例如草稿包含“title A → B”，最终对象却写成 “title C”，或者中间一次变更的 `from` 与上一次的 `to` 不一致，仍可能进入只读审查。

新增 `src/container-project-intent-audit.js` 对导入的最终对象快照进行**逆序状态回溯**：每个修改的 `to` 必须等于当前逆序状态，然后以 `from` 撤回；同对象、同字段的下一步必然核对上一步。校验包含：

- 按升序唯一的 revision（允许 Undo 所致间隔）及不得超过工程 revision；
- `include` 只能布尔、`reorder` 只能在既有对象数量内的整数；
- `set-attribute` 只能操作此对象类型明示支持的字段，`from` 允许 `null` 表示属性原先缺失；
- 所有操作都必须产生真实值变化，不能借空操作伪造历史；
- 导入记录末值必须与导入的最终对象快照一致，否则拒绝 JSON 而不是沉默忽略。

用户可在“草稿修改记录（只读）”中展开最多 12 条明细，同时看到总计数。场景测试在**真实 Chromium** 上用可见工程草稿入口读入正确和矛盾的 JSON，原有媒体、封装计划及下载保持不变；全量 P0/P2/P3/Batch E2E 继续作为合并门槛。

## 明确的信任边界

一个经过蓄意篡改、但**内部自洽**的 JSON 仍可通过此检查。因此 `internallyCoherent=true` **不证明**记录来自原作者、原本发生过这些编辑、SHA 来源身份、目标对象与正在编辑的来源一致，也不授予自动回放 / 用户文件修改 / Matroska 写入权限。

完整 SHA-256（PR #122）只证明与**用户提供的摘要声明**相符，不能代替可信签名或真实来源对象的结构化验收。未通过后续验证的草稿没有任何执行权限。

## 理论初版的未完成项

当前导入的 `ContainerProject` 仍是独立只读草稿，未替换产品的真实可写编辑权威。尚未实现：通过源身份+对象结构+意图意外冲突复核的显式用户确认/事务应用、任意安全 MKV EBML 写入、持久操作恢复、大文件真实压力和跨播放器矩阵。单个有效样本不能提升到 UIGS Canonical。
